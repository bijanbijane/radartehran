## 1. Governance Principles & Status Definitions

Every Cloudflare capability is evaluated against 11 mandatory governance questions (real requirement solved, existing solution status, measurable advantage, account/plan/geographic eligibility, runtime compatibility, limits/failure modes, cost, state ownership, replacement difficulty, and immediate justification).

- **Statuses Used (Section 17 Canonical Taxonomy)**:
  - `DISCOVERED` / `RELEVANCE ASSESSED` / `NOT CURRENTLY NEEDED` / `ARCHITECTURAL PREPARATION COMPLETE`
  - `IMPLEMENTED_IN_SOURCE`: Adapter, Worker runtime (`worker/**`), and configuration code (`wrangler.jsonc`) are implemented in repository.
  - `TESTED_LOCALLY`: Verified via local simulator and Wrangler dry-run packaging checks.
  - `TESTED_WITH_LOCAL_SQLITE`: Verified against real SQLite (`node:sqlite` `DatabaseSync` and `wrangler d1 migrations apply --local`).
  - `REMOTE_RESOURCE_PROVISIONED` / `REMOTE_MIGRATIONS_APPLIED` / `REMOTE_DEPLOYED` / `LIVE_HTTP_VERIFIED` / `LIVE_BROWSER_VERIFIED`: Reserved strictly for verified remote executions.
  - `BLOCKED_BY_EXTERNAL_REQUIREMENT` / `BLOCKED`: Requires external Cloudflare account credentials (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`), domain delegation, or regional payment eligibility not mounted in the sandbox.
  - `DEFERRED`: Intentionally deferred until scale or external triggers justify activation.
